REDLINE

C++ / CUDA LLM inference runtime

Redline serves Llama-family models on a single GPU. It manages its own paged KV cache, scheduling, sampling and GPU memory, and decodes with INT8/INT4 weight-only kernels, CUDA graphs and speculative decoding. This page walks through one decode step and the ideas that make it fast. Each idea has a live figure and links to the code that implements it.

02

Keeping the GPU busy: async scheduling and CUDA graphs

Talk track
  • In a naive loop the GPU idles while the CPU reads the sampled token, checks stop conditions and builds the next batch.
  • Redline launches step t+1 before reading step t. Next-step inputs come from the device, so the host never sits on the critical path.
  • A decode step is a few hundred small kernels. Launched one by one, the CPU cost can exceed the GPU work, especially for the small draft model. A CUDA graph replays the whole step with one launch. Switch the model to the 1B draft to see it.
Assumptions

Times come from a model with editable inputs, not measurements. Kernel counts are Redline's real launches per step: 10 per layer plus 6. GPU work defaults to the bandwidth-bound step time from section 04 at roughly 85% efficiency. Measured step times are in section 06.

03

Paged KV cache and continuous batching

Talk track
  • The KV pool is one GPU allocation cut into 16-token blocks. A sequence owns a list of block ids (its block table), so memory grows a block at a time and never needs to be contiguous.
  • Every step the scheduler gives each running sequence one decode token first, then spends the remaining token budget on prefill chunks and new admissions.
  • When the pool runs dry, the newest sequence is preempted. Its blocks are freed and it is recomputed later, so older requests keep their latency.
What you are seeing

A JavaScript port of Scheduler::schedule on a small pool. Each square is a block, labeled with the sequence that owns it. Shrink the pool to force preemption.

04

Why INT4 decodes faster: bytes moved per token

Talk track
  • At small batch sizes decode is memory-bound. Every step streams every weight once, so step time is roughly bytes read ÷ memory bandwidth.
  • INT8 halves and INT4 quarters the weight traffic. The GEMV kernels dequantize in registers, so the GPU never writes an FP16 copy of the weights.
  • KV traffic grows with batch × context. Redline's attention reads each K/V vector once per GQA group instead of once per query head, which is 4× less for Llama 3.
Assumptions

These are bandwidth ceilings computed from the model's real shapes and the GPU's spec-sheet bandwidth. Real kernels reach a fraction of this, and the measured numbers come from redline_bench.

05

Speculative decoding

Talk track
  • A small draft model (Llama 3.2 1B) proposes k tokens. The 8B target checks all of them in one forward pass, which costs about the same as one decode step because decode is memory-bound.
  • A GPU kernel accepts draft token i with probability min(1, ptarget/pdraft) and resamples the first rejection from the leftover distribution. The output has exactly the target's distribution.
  • The benchmark reports the acceptance rate. More draft tokens only help while acceptance stays high, and the chart shows where that stops paying.
